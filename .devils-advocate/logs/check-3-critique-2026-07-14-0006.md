## Failing criteria (numbered, with fixes)

### 1. patterns-correct / edge-cases — `handle.exe` is a confident FALSE NEGATIVE (real Sysinternals tool wrongly marked "not invoked")

`tool_purposes.py:32` (BIN/handle.exe):
> "…the automated script match was a false positive (matched the unrelated phrase 'handle ownership issues'
> in a GUI code comment) — **no confirmed direct invocation found in the reviewed scripts.**"

This is false. `handle.exe` (Sysinternals Handle) is **actively invoked** in two live code paths:
- `extracted/TSS_SHA.psm1:1295` — inside `function CollectSHA_support-handleLog`:
  `"$global:ScriptFolder\BIN\handle.exe -a /AcceptEula | Out-File ${LogFolder}\..._handle.txt"` → `RunCommands`
- `extracted/TSS.ps1:7262` — inside a `Test-Path $HandleExe` block:
  `"handle.exe -a /AcceptEula | Out-File -Append $outFile"` → `RunCommands`

Root cause: `gen_tool_inventory.py:16-26` `find_refs()` caps at `max_refs=3` and `return`s early. The first
three "handle" substring hits are all GUI false positives in `TSSGUI.ps1:215/216/218` ("handle ownership
issues", "FromHandle", "Release the handles"), so the two real invocations never entered the evidence set.
The author then read only the false-positive evidence and concluded non-invocation. A reader of Section 7
is told a genuinely-run, high-signal Sysinternals handle-enumeration tool is not used — the opposite of the
truth. **Fix:** raise/remove the 3-match cap (or prefer non-comment, non-`::`-changelog lines when
selecting evidence), then re-review `handle.exe`; its purpose should read as a confirmed invocation with
`-a /AcceptEula` (evidence TSS_SHA.psm1:1295 / TSS.ps1:7262). Also correct the Section-7 caveat, which
currently lists "handle" as a false-positive **exemplar** — it is not one.

### 2. no-hacky-shortcuts / patterns-correct — evidence column silently shows false-positive substring matches for confirmed tools, contradicting the doc's own "explicitly flagged" caveat

`gen_tool_table.py:18` uses `r["refs"][0]` — the first grep hit, unconditionally. When the first hit is a
substring-inside-a-word false positive, the table presents gibberish as the "Invocation evidence (file:line)"
for a tool whose Purpose is nonetheless confidently asserted. Section 7's caveat promises FP cases "are
explicitly flagged below as unconfirmed rather than presented as verified instrumentation" — but these are
not flagged:
- `BINx64/Pstat.exe` & `BINx86/Pstat.exe` (`tool_inventory_final.json`) — evidence
  `TSS.ps1:2898: if($r.Name -eq 'Instance' -and $resp.StatusCode…` ("pStat" matched inside **HttpStatusCode**).
  Real path construction is `TSS.ps1:32216 $global:PstatExe = …\Pstat.exe`. Purpose ("path constructed and
  referenced in TSS's core status-collection logic") is fine; the **displayed evidence is a false positive**.
- `BINx64/latte.exe` — evidence `TSS.ps1:12626: # Cut out the latter part to combine later` ("latte" matched
  **latter**). Real invocation is `TSS.ps1:30426 $LatTeExe + " -a " + $PerfTCPAddr + ":5005 -i 10010"`.
- Broader: of the 94 "has evidence" rows, only **62** cite an actual invocation-looking line; **32** cite a
  comment (26) or dated changelog `::` line (6). Many comment lines are harmless (adjacent to the real call),
  but Pstat/latte show the column can actively mislead. **Fix:** in `find_refs`, skip lines whose match falls
  inside a longer alphanumeric token (word-boundary check) and de-prioritize `#`/`::` comment lines, so the
  cited evidence is a real invocation; or, where only FP hits exist, emit "No confirmed invocation" rather
  than a misleading line.

### 3. patterns-correct (lower severity) — `SAN.exe` reasoning is wrong and its purpose is under-confirmed

`tool_purposes.py:103` (psSDP/Diag/global/SAN.exe): says the match was "a false positive on an unrelated
GUI/Copilot function name" and purpose is "not independently confirmed… though the name suggests a Storage
Area Network diagnostic tool." A real, on-point reference exists:
`extracted/psSDP/Diag/global/DC_SanStorageInfo.ps1:16` — `$CommandToExecute = "cmd.exe /c SAN.exe $CommandToAdd"`
inside a script literally named DC_**SanStorageInfo** that builds `_Storage_Information.txt`. This directly
corroborates the "SAN storage" purpose. Mitigating fact: that block sits inside a commented-out
`#region 'Old Code' <# … #>`, so "not actively invoked" is defensible — but the stated *reason* (Copilot
function-name collision) is wrong, and the hedge understates that the toolkit itself names this a SAN storage
tool. Same 3-match-cap root cause (the real ref was crowded out by GUI matches). **Fix:** cite
DC_SanStorageInfo.ps1:16, note it is present-but-in-a-disabled block, and drop the incorrect "Copilot
function name" explanation.

### Additional note (not counted as a separate failure)
`BIN/nvspinfo.exe` (`tool_purposes.py:36`) states the script "actually invokes companion .js files … rather
than this .exe directly." But `TSS_SDP.psm1:8307-8310` does locate and use the exe (`Get-Command nvspinfo.exe`,
`Test-Path "$global:ScriptFolder\BIN\nvspinfo.exe"`, copies it to remote nodes). The characterization is
inaccurate, though it is explicitly hedged "not confirmed," so it degrades gracefully.

## Caveat-placement assessment (task item 7)
The Section-7 caveat paragraph is positioned **before** the table (good) and states the two right ideas
(short-name FPs; "not independently confirmed" = inference). Two weaknesses: (a) its FP exemplar list
"du/kd/SAN/handle" is itself partly wrong — `handle` is a real invocation and `SAN`'s reference corroborates
its purpose; (b) because per-row FP evidence is not flagged inline (item #2), a reader skimming the table
still over-trusts rows like Pstat/latte whose evidence line is gibberish. The caveat's promise ("explicitly
flagged below") is therefore not fully kept at the row level.
