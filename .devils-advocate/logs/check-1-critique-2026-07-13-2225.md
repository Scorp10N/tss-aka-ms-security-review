## Failing criteria

### 1. patterns-correct — "signed" = string-presence, not signature verification
`scripts/gen_bom.py:34-50` determines `signed=True` purely from whether `openssl pkcs7 -print_certs -noout`
emits at least one `subject=` line, then records `subjects[0]` as the signer. It performs **zero cryptographic
validation**: no Authenticode digest recomputation, no verification that the PKCS#7 signature is valid over the
PE hash, no chain construction to a trusted root, no revocation, no timestamp check. A tampered binary carrying
any well-formed PKCS#7 blob with a `CN=Microsoft Corporation` subject would be reported `signed=true, signer=Microsoft Corporation`.
The committed script also **never captures issuers**, yet Report §3.4 asserts specific issuing CAs ("Microsoft
Code Signing PCA 2010/2011/2024 or Windows Production PCA") — that detail is not reproducible from the committed
artifacts (I had to add issuer extraction myself to confirm it; it is in fact true, but the pipeline doesn't show it).
**Fix:** use `osslsigncode verify` (or signtool) to actually validate the signature + chain; or, if keeping the
lightweight approach, rename the field to `has_embedded_cert_blob`/`embedded_signer_subject` and state plainly that
this is blob-presence, not signature validation. Capture issuer alongside subject if §3.4 is going to cite CAs.

### 2. no-reinvention — hand-rolled PKCS#7 parsing instead of a real Authenticode verifier
Both scripts hand-parse the `WIN_CERTIFICATE`/`IMAGE_DIRECTORY_ENTRY_SECURITY` structure and shell out to
`openssl pkcs7 -print_certs` (gen_bom.py:34-50, extract_sig.py:19-41). `osslsigncode` (cross-platform) or
Windows `sigcheck`/`signtool` would perform real Authenticode verification more reliably. §3.4.1 discloses that
full chain / CRL / OCSP / RFC3161 timestamp were **not** verified (good), but it does **not** disclose that the
"signed" determination itself is merely subject-string presence rather than any signature check.
**Fix:** adopt osslsigncode, or add one sentence to §3.4/§3.4.1 stating the `signed` flag reflects presence of an
embedded Microsoft-subject certificate blob only, not cryptographic validation.

### 3. imports-correct — extract_sig.py hardcodes a session-specific absolute path
`scripts/extract_sig.py:30` writes to
`/tmp/claude-1000/-home-yarin-Projects/8eb9bcaa-a105-4e06-a715-4bb256cf86c4/scratchpad/tss/{name}.p7`.
This absolute path (a) embeds the author's local session/scratchpad directory structure into a **public** repo,
and (b) requires the `tss/` subdir to pre-exist — on any fresh clone or other machine `open(sig_path,'wb')` raises
`FileNotFoundError` and the utility crashes before printing anything. (It only "works" in this review because the
same session id happened to recreate that path.)
**Fix:** `import tempfile; sig_dir = tempfile.mkdtemp()` or `os.makedirs('sigs', exist_ok=True)` with a relative
path; remove the machine-specific absolute path from the committed source.

### 4. no-hacky-shortcuts — confident signing language outruns the actual method; one inaccurate provenance detail
Report §2 method bullet says the review "validated certificate chain subjects/**issuers** via OpenSSL" and §4 risk
table rationalizes "valid Microsoft signatures on all functional binaries," framing signing as essentially settled,
while the committed pipeline only extracts leaf subject strings (no chain build, no issuer capture, no crypto verify).
The §3.4.1 disclosure ("full X.509 chain-of-trust / CRL / OCSP / timestamp not verified") is good and partially
rescues this, but the disclosure and the confident body framing sit in tension. Separately, §3.5 claims
microsoft/TSS.MSR was confirmed unrelated "via **empty/irrelevant release history**" — the repo is actually active
(pushed 2026-04-18); it is unrelated (a TPM stack), but it is not "empty."
**Fix:** align the §2/§4 wording with what was done ("extracted and inspected subject/issuer strings"); correct the
"empty release history" phrasing to "active but unrelated (TPM 2.0 software stack)."
