## MAIN FINDING — root cause fixed, but a new latent nondeterminism took its place

`find_refs()` (gen_tool_inventory.py:57-74) now collects **every** substring match and sorts:
```python
candidates.sort(key=lambda c: -c[0])   # score only; NO secondary key
top = candidates[:max_refs]
```
Python's sort is stable, so ties are resolved by **insertion order = `os.walk("extracted")`
iteration order**, which Python explicitly does **not** guarantee (not sorted; filesystem/readdir
dependent). I proved the exposure two ways:

1. **Determinism within an environment holds:** ran the script twice in fresh processes →
   `tool_inventory.json` byte-identical; regen == committed. So on Linux+`unzip` it reproduces.
2. **Tie-break is traversal-order-dependent:** I precomputed every binary's candidate set (scores
   are order-independent), then re-sorted under 200 shuffled orderings. **62 of 115 binaries change
   their displayed `refs[0]` under a different traversal order.** Representative tie widths at the
   top score: Showpriv.exe **92 tied**, kd.exe 99, procdump 56, wpr 36, devcon 29, Procmon 25,
   dfsutil 22, handle 20, DiagPackage 20.

**Why it matters / why it's lower severity than check #4's bug:** for the large majority of the 62,
every tied line is an *equally-valid* invocation in the same function/block (e.g. accesschk
TSS_NET.psm1:3042-3045; devcon TSS_SDP.psm1:4507-4533) — so the *conclusion* (purpose) is
unaffected; only *which equivalent line is printed* could vary on another filesystem. No wrong
purpose results. That is a genuine improvement over check #4, where the defect produced false
NEGATIVES. But it is still a real defect: the report's method text claims it cites "the
highest-scoring lines," which is under-defined when 54% of rows have score ties, and the committed
artifact is not guaranteed byte-reproducible on an arbitrary filesystem (only on one whose walk
order matches the author's). The correct fix is one line:
`candidates.sort(key=lambda c: (-c[0], c[1], c[2]))` (path, then line) — provably deterministic on
any host, and removes the accidental dependence on `os.walk` order.

### The one case where the tie surfaces a genuinely worse line: handle.exe
Evidence displayed: `TSS_SHA.psm1:1292: $LogFolder = "$global:LogFolder\support...\handle"` — a
log-folder path string, **not** an invocation. The real invocation is 3 lines below at
`TSS_SHA.psm1:1295: ...\BIN\handle.exe -a /AcceptEula | Out-File ...`, which the **purpose text
correctly cites**. Both score 7 (1292 gets word-boundary +3 on `\handle`, non-comment +2,
`$global:` marker +2; 1295 gets wb +3, non-comment +2, `.exe` marker +2), so the tie-break picks
the earlier line. Net: for the *very first binary check #3 flagged*, the "invocation_evidence"
column still shows a non-invocation line that disagrees with the purpose's own cited line. Purpose
is right; the evidence cell is misleading. This is a residual instance of check #3's original
"evidence column is unreliable" complaint — narrowed, not eliminated.

### Systematic evidence-column weakness (variable-indirected tools)
For tools called via a `$global:XxxExe` variable, the **path-definition line** (`...\Xxx.exe`, a
word-boundary hit) outscores the actual **invocation** line (which uses `$global:XxxExe` where the
basename is glued to `Exe` and loses the word-boundary bonus). So du.exe evidence = the path-def
`TSS.ps1:32213` (not the real `TSS_SHA.psm1:3036-3038 "$global:DuExe -accepteula -q -v ..."`), and
tmq.exe evidence = `TSS_INT.psm1:29` (not `:232-242 "$global:TMQexePath state|site|store -v"`).
Not *wrong* — those purposes lead with "path constructed at ..." so evidence and purpose agree —
but the evidence cell rarely shows an actual command line for this whole class. Cosmetic/quality,
not a failing conclusion.

## Failing criteria (numbered, with fixes)

### 1. no-hacky-shortcuts — candidate sort has no deterministic tie-break (latent nondeterminism)
`gen_tool_inventory.py:72` sorts by score only; ties fall to `os.walk` traversal order, which is
filesystem-dependent and not guaranteed stable. Proven: 62/115 binaries change their displayed
`refs[0]` under shuffled traversal order. **Fix:** `candidates.sort(key=lambda c: (-c[0], c[1],
c[2]))` — deterministic on any host, removes the accidental reproducibility dependence, and (bonus)
makes the choice among equal-score lines the lowest-path/earliest-line, which is defensible and
documentable. Optionally note in the Section-7 method text that among tied top-score lines the
lowest-path/earliest is shown.

### 2. edge-cases — top-score ties surface weak/non-invocation lines (handle.exe) and are unstable
The "many lines tie at max score" case is unhandled: handle.exe displays `TSS_SHA.psm1:1292`
(a `$LogFolder` path string) as invocation_evidence while the purpose cites the real invocation at
`:1295`. **Fix (data-quality layer, on top of #1):** either (a) add a small MANUAL_EVIDENCE_OVERRIDE
for handle.exe pointing at `TSS_SHA.psm1:1295`, or (b) refine scoring so a line whose ONLY marker is
`$global:`/`test-path` (i.e. a path/log-folder assignment with no `.exe`/`cmd.exe`/`start-process`/
`out-file` command token) scores below a line carrying an actual command token — which would let the
real invocation line win outright for the whole `$global:XxxExe` class (du/tmq/handle) without
per-entry overrides. (b) is the systemic fix; (a) is the cheap patch.

## Bottom line

The 70fe55b patch **answers the central question with a qualified YES on correctness**: the du/tmq
false negatives, the cdb under-confirmation, and the 695-vs-692 undercount are all genuinely fixed
and independently re-verified, and no wrong purpose survived a 115-row contradiction sweep plus 20

and the sort has no deterministic secondary key — so the displayed evidence line is chosen by

non-invocation line disagreeing with its own purpose. The conclusions are sound and reproduce
byte-identically here; the *evidence column's reliability and cross-filesystem reproducibility* are
the remaining gap, fixable with a one-line deterministic sort key plus one scoring tweak (or a
handle.exe override).
