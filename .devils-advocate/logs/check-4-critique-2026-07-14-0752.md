## THE MAIN FINDING — the patch moved the bug (root cause: 40-candidate cap runs BEFORE scoring)

`find_refs()` (gen_tool_inventory.py:47-64) collects up to `max_candidates=40` substring matches **in file
iteration order**, `break`s, and only THEN scores + sorts. So the scoring never sees any line beyond the
40th substring hit. For a basename that is a high-frequency substring, the real invocation line is hit
far later than position 40 and is silently invisible to the scorer — identical mechanically to the SAN
case, which is why SAN needed a manual override. **The scoring patch improved ranking *within* the
40-line window but did nothing about lines outside it.** I enumerated every binary with >40 substring
matches and compared the capped-top evidence to an *uncapped* scored search; 10 differ, and two of those
are hedged purposes that are actually wrong:

| binary | substr matches | purpose says | reality (uncapped) |
|---|---|---|---|
| BINx64/du.exe | 12,175 | "no confirmed direct invocation found (matches were false positives)" | **actively invoked** |
| BINx86/du.exe | 12,175 | same | **actively invoked** |
| BINx64/tmq.exe | 1,180 | "No confirmed direct script reference … false positive" | **actively invoked** |

### du.exe — confident FALSE NEGATIVE (Sysinternals Du, actively run)
- Path def: `extracted/TSS.ps1:32213` — `$global:DuExe = $global:ScriptFolder + $BinArch + "\Du.exe"`
  (same block, same style as `$global:HandleExe` / `$global:PstatExe`, both of which the report treats as
  real references).
- Invoked: `extracted/TSS_SHA.psm1:3027-3038`, inside `CollectSHA_SpaceInfo`-style disk-space collection:
  `"$global:DuExe -accepteula -q $drivename\ > ..._du.txt"`, `-q -l 1`, `-q -v` variants — written into a
  `$DriveSpaceCommands` **.bat that is registered and run via `schtasks /create … /run`**, and repeated in
  a live `$Commands = @(…)` RunCommands array. This is active execution, not dead code.
- The purpose ("no confirmed direct invocation found … automated matches were false positives") is the
  exact opposite of the truth — a genuinely-run Sysinternals disk-usage enumerator reported as not used.
  **Root cause:** "du" has 12,175 substring hits ("Introduction", "product", "module", every URL…); the
  40-candidate cap fills with GUI/URL noise (capped-top = `aka.ms/TssInfo`, score 2) long before reaching
  TSS.ps1:32213 or TSS_SHA.psm1:3027. **du.exe needed the same MANUAL_EVIDENCE_OVERRIDE that SAN got, and
  is a stronger case than SAN because it is active, not commented-out.**

### tmq.exe — confident FALSE NEGATIVE (MSMQ diagnostic, actively run)
- Path def: `extracted/TSS_INT.psm1:29` — `$global:TMQexePath = $global:ScriptFolder + $BinArch + "\TMQ.exe"`.
- Gated + invoked: `TSS_INT.psm1:223` `if (Test-Path $global:TMQexePath){`, `:224` logs
  `"collecting TMQ.exe info"`, `:232-242` build `"$global:TMQexePath  state|site|store … | Out-File …"`
  MSMQ queue-dump commands. Fully active.
- The purpose ("the one substring match found was inside an unrelated base64-encoded certificate blob, a
  false positive") is false. **Internal inconsistency:** the report *confirms* `tmqstate.dll` citing
  `TSS_INT.psm1:238` — which is literally one of the lines that invokes `$global:TMQexePath state`. So the
  report confirmed the DLL sub-verb while declaring the parent .exe a false positive, from the same block.
- Root cause: 1,180 substring hits, mostly "TMQ" inside base64 cert blobs in `scripts/Wmi-Collect.ps1`
  (capped-top is one such blob, score **-5** — the encoded-blob penalty fired correctly but is powerless
  when the *real* line is outside the 40-window). Needed a manual override; didn't get one.

The other 8 cap-divergences (Procmon×2, wpr, xperf, livekd, du already listed, cdb, DiagPackage) have
**correct purposes** — only the *displayed* evidence line is a weaker/GUI line than the real invocation
(e.g. wpr.exe shows `$parameterType = "WPR"` instead of `wpr.exe -BootTrace -cancelboot`; handle.exe's
displayed evidence is `[Switch]$noHandle` rather than `handle.exe -a /AcceptEula`). Lower severity, but
same mechanism: the evidence column is still not reliably the strongest line for any high-frequency name.

## Case-sensitivity finding — "all 695 scripts searched" is inaccurate (692 actually searched)
The glob in `gen_tool_inventory.py:10` is case-sensitive (`*.ps1` / `*.psm1`). The archive contains 3
uppercase `.PS1` files that are silently skipped:
`scripts/KipG-Scripts/{SysvolReplConvergence,ShowBackup,ADReplConvergence}.PS1`. So the script searches
**692** files, while README, `gen_report.py`, `gen_tool_table.py` (twice), `tool_purposes.py`, and the
DOCX (23 occurrences) all claim **695**. Impact on conclusions: **nil** — I grepped all three files for
every PE basename (word-boundary) and found zero PE references — but the completeness claim is overstated
and the "no direct reference found (695 … searched)" boilerplate is literally false for the 21
not-referenced rows. Fix: `glob(..., *.[pP][sS]1)` / case-insensitive, or correct the number to 692.

## Failing criteria (numbered, with fixes)

### 1. patterns-correct — du.exe (×2) and tmq.exe are confident FALSE NEGATIVES; caveat prose names them as FPs
Fix: correct the three purposes to "confirmed actively invoked" —
- du.exe (both): `$global:DuExe` defined `TSS.ps1:32213`; invoked `TSS_SHA.psm1:3036-3038` (also a
  scheduled `.bat`) as `Du.exe -accepteula -q [-l 1] [-v]` → per-drive `_du*.txt`. Sysinternals Du.
- tmq.exe: `$global:TMQexePath` `TSS_INT.psm1:29`; `Test-Path`-gated `:223`; invoked `:232-242`
  (`state`/`site`/`store -v` → `TMQ-*.txt`). MSMQ diagnostic.
Then rewrite the Section-7 caveat: kd is a valid FP exemplar; du and tmq are NOT — replace them (e.g. with
truly-unreferenced names like `vssagent`, `xbootmgr`, `WSRUNAMD64`) or drop the specific list.

### 2. edge-cases / no-hacky-shortcuts — the 40-candidate cap runs before scoring; root cause unfixed
`find_refs()` scores only the first 40 substring hits. Fix the class, not the instances: either (a) score
lines *during* collection and keep a top-K heap over ALL matches (still O(n), no cap needed), or (b) run
the word-boundary regex first and cap on *word-boundary* candidates (word-boundary hits for du/tmq/SAN are
few), or (c) at minimum extend MANUAL_EVIDENCE_OVERRIDES to du.exe×2, tmq.exe, cdb.exe. Option (a) is the
correct fix and removes the need for a growing override dict.

### 3. naming-matches — "695 scripts searched" is 692 in reality (case-sensitive glob skips 3 `.PS1`)
Fix: make the glob case-insensitive (`glob('extracted/**/*.[pP][sS]1', recursive=True)` +
`*.[pP][sS][mM]1`), which restores the real 695 and searches the 3 skipped AD-replication scripts; or
correct every "695" to "692". Impact on current conclusions is nil (those 3 files contain no PE refs),
but the number is repeated 23× in the shipped DOCX.

### (not a separate criterion) cdb.exe under-confirmation
Correct "could not be reliably attributed to a specific invocation" — `TS_DumpCollector.ps1:54`
(`/cdbpath:$Global:ToolsPath\cdb.exe /debuginfo`, active) is a specific attribution.

## Bottom line
Reproduction is byte-exact and the counts reconcile. The hand-authored purpose dict is high quality — of
~55 entries personally verified, all but du×2/tmq/cdb are accurate, and handle/Pstat/latte/SAN are
genuinely fixed. But the cbaef47 patch answered "did the fix hold?" with a partial no: it repaired the
individual entries someone re-read and added a sound override *seam*, yet left the **root cause** (cap
before scoring) in place, so two active tools (Sysinternals Du, MSMQ tmq) remain confident false
negatives — and the caveat text now teaches the reader that those two are safely-flagged false positives.
The bug was relocated, not eliminated.
