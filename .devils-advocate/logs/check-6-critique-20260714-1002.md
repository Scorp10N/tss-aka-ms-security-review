## Result: 17/22 PASS

### Failing criteria (fixes)

**1. patterns-correct / no-hacky-shortcuts — `chain_verified` parser can report TRUE on a FAILED chain.**
`osslsigncode_info()` decides the chain result with:
```python
if "Signature verification: ok" in out or "Signature verification: succeeded" in out:
    info["chain_verified"] = True
elif "Signature verification: failed" in out:
    info["chain_verified"] = False
```
The substring `"Signature verification: ok"` is **also contained in** osslsigncode's timestamp line `"Timestamp Server Signature verification: ok"`. Because it's `if/elif`, that timestamp line satisfies the `if` and short-circuits the `elif` — so any binary whose **primary signing chain fails but whose timestamp verifies** is misclassified `chain_verified=True`.
*Demonstrated (fault injection):* genuine xperf.exe with `-CAfile` = Root 2011 only (so the Root-2010 signing chain cannot build) and `-TSA-CAfile` = Root 2010 (timestamp OK). osslsigncode returncode **1**, real summary line **`Signature verification: failed`**, `Error: unable to get local issuer certificate` — yet the parser returns **`chain_verified=True`**.
This does **not** affect the current committed numbers (all 114 genuinely pass, which I reproduced), but it is a latent **false-confidence defect in the security-verification mechanism** — the most consequential class per this check's mandate. A future TSS update signed through a chain the bundled roots don't cover, or a revoked-but-timestamp-valid cert, would be reported "verified."
*Fix:* anchor to the primary result line and/or use the exit code, e.g.
```python
m = re.search(r"(?m)^Signature verification: (ok|succeeded|failed)\b", out)
if m:
    info["chain_verified"] = m.group(1) != "failed"
# or simply: info["chain_verified"] = (result.returncode == 0) when signed
```
osslsigncode already exits 0/1 cleanly; the code captures `result` but never reads `result.returncode`.

**2. types-consistent / naming-matches — bom.json `verification_method` is stale and self-contradictory.**
The committed field still reads: *"…full chain-to-root verification = chain_verified, requires local Microsoft root CA trust store which was not configured, so chain_verified is expected to read false/failed even for genuine binaries."* Meanwhile all 114 rows in the same file read `chain_verified: true`, and the DOCX/README declare the gap closed. `git show HEAD -- bom.json` confirms this line was **not** touched by 2c17a5a — contradicting the commit message's claim that "bom.json's verification_method field was updated." Worse, `gen_bom.py` **hardcodes** this stale string, so every re-run regenerates the contradiction (I confirmed my regenerated bom.json carries it too). The machine-readable field is the part downstream tooling would trust.
*Fix:* update the `verification_method` string literal in `gen_bom.py` to describe the now-configured chain/TSA/CRL verification, and regenerate bom.json/bom.csv.

**3. edge-cases — ambiguous osslsigncode output unhandled.**
Same root cause as #1, distinct lens: the code assumes exactly one "Signature verification:" token, but osslsigncode emits several ("Timestamp Server Signature verification: ok", "Signature CRL verification: ok", "Signature verification: ok/failed"). Only the last, column-0, unprefixed line is the verdict. Covered by the #1 fix (line anchor).

**4. naming-matches — ms-roots/README.md provenance table references 6 non-existent files.**
The table's "File" column lists `MicRooCerAut_2010-06-23.pem`, `root2011.pem`, `intermed_codesign2010.pem`, `intermed_codesign2011.pem`, `intermed_codesign2024.pem`, `intermed_winprod2011.pem`. `git ls-files ms-roots/` shows only `ms_roots_ca.pem`, `ms_intermediates.pem`, `README.md`. A reader following the table to `openssl x509 -in ms-roots/MicRooCerAut_2010-06-23.pem` gets file-not-found. (The certs themselves *are* present inside the two bundles, so this is documentation-accuracy, not a security hole.)
*Fix:* either commit the 6 individual PEMs, or reword the table to state the individual files are concatenated into the two shipped bundles (their per-cert identity is recoverable via `openssl storeutl -certs` / splitting on the PEM boundary).
